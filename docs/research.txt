globals (GetSpellInfo, IsSpellKnown, GetItemCount, UseItemByName,
CastSpellByID for crafting). This build is retail-shaped minus the
stats/specialization layer - use C_Spell / C_Item / C_TradeSkillUI
namespaces, and when a namespace's exact function name isn't already
confirmed, discover it by dumping real key names rather than guessing.

Also confirmed via warcraft.wiki.gg: C_TradeSkillUI.CraftRecipe's real
signature is:
  C_TradeSkillUI.CraftRecipe(recipeSpellID, numCasts, craftingReagents,
    itemTarget, applyConcentration)
all but recipeSpellID optional. For our fixed-reagent recipes (no
reagent choices, no concentration system on this build), a bare
CraftRecipe(recipeSpellID) call should be enough to test.

H3. MAJOR FINDING. C_Item.UseItemByName cannot be called from /run (or
   from any ordinary insecure Lua, including a normal Button's OnClick)
   at all - confirmed via the function itself, citing
   warcraft.wiki.gg's SecureActionButtonTemplate page. It requires
   secure code execution.
   RESOLVED/CORRECTED (open question c, AND definition.md's framing of
   "biggest open risk"): using/placing the crafted item is NOT a matter
   of calling a function from our own OnClick handler - it needs a
   SecureActionButtonTemplate-based button with secure attributes set
   ahead of time (SetAttribute("type","item"), SetAttribute("item",
   <name or itemLink>)), with Blizzard's own C code performing the
   protected action when the button is physically clicked. This is the
   same mechanism action bars use - still achievable as "one click" from
   the player's perspective, but architecturally that one button can't
   be a plain Button+OnClick calling our Lua like the rest of the UI;
   it needs the secure-template treatment specifically for item use.
   Whenever which item is "current" changes (e.g. profession/available
   good changes), the fix is to update the button's secure attributes,
   not to call a function.
   NOTE: G's CraftRecipe call did NOT throw this same error - suggesting
   crafting itself is NOT similarly protected, only the use/placement
   step is. If N confirms G's craft actually completed, this means
   definition.md's current "silent crafting is the biggest open risk"
   framing has it backwards - crafting looks straightforward from
   ordinary addon code; using/placing the result is the part that
   needs the secure-template approach. Worth correcting definition.md
   once N confirms.
